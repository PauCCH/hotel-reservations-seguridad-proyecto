PoC AUD-POC-4 (F2.2 — Vector 2, XSS stored vía metadata del log)
================================================================

Entorno: panel-admin local (localhost:3002), build dev, migraciones aplicadas
hasta 20260922000002_create_audit_logs_table.sql.

No se necesita sesión ni cuenta: el punto de entrada es el propio formulario
de login público (/auth/login), sin autenticar.

Código vulnerable (sumidero / sink):
  apps/panel-admin/src/features/audit-log/components/AuditLogDetailDrawer/AuditLogDetailDrawer.tsx:65-69
    <div
      className={...}
      dangerouslySetInnerHTML={{ __html: formatMetadataHtml(row.metadata) }}
    />

  packages/core/src/audit/shared/utils.ts:74-87 (formatMetadataHtml)
    El propio comentario del código lo admite: "Values are interpolated
    as-is (no HTML escaping) so the consumer can opt into
    dangerouslySetInnerHTML." Cada valor de metadata se interpola crudo en
    un string HTML (`<span class="audit-meta-value">${rendered}</span>`),
    sin pasar por ningún escape/encode.

Código vulnerable (punto de entrada / fuente):
  apps/panel-admin/src/features/auth/services/loginAction.ts:15,25-31
    const email = formData.get("email") as string;   // sin validar

### Paso 3 — ejecución (confirmación por inspección de código, no por
navegador — esta sesión no tiene una herramienta de automatización de
navegador conectada)

`row.metadata` (tal cual se ve arriba) se pasa a `formatMetadataHtml`, que
devuelve el string:
  `<div class="audit-meta-row"><strong>email</strong><span class="audit-meta-value"><img src=x onerror="document.title=AUD-POC-4-XSS"></span></div>`
y ese string se inyecta sin más mediante `dangerouslySetInnerHTML` en
`AuditLogDetailDrawer`. Un `<img>` con `onerror` insertado vía `innerHTML`
SÍ ejecuta su manejador de evento al fallar la carga de `src=x` (a
diferencia de un `<script>` inyectado por innerHTML, que el navegador no
ejecuta) — es el vector estándar para XSS stored a través de
`dangerouslySetInnerHTML`/`innerHTML`.

**Para confirmar visualmente:** iniciar sesión en el panel como cualquier
admin, ir a `/admin/audit-log`, filtrar por `auth.login.failed` y abrir el
detalle de la fila con id `b722a112-0e26-4b0d-a578-c0f6f079e6c2` (o repetir
el Paso 1). El título de la pestaña del navegador cambia a
"AUD-POC-4-XSS", confirmando ejecución en el contexto de la sesión admin
autenticada (en un ataque real: robo de sesión, acciones con los
privilegios del admin, pivoteo a otros módulos).

Impacto: XSS stored, sin autenticación para inyectar (cualquiera en
internet puede intentar un login con un email malicioso), que se ejecuta
en el navegador de CUALQUIER admin que abra el visor de auditoría —
incluyendo cuentas owner. Combinado con AUD-POC-1 (acceso sin audit:view),
el payload es visible para el conjunto más amplio posible de admins.

Clasificación: REAL. Es exactamente la cadena O3/AU-R01 de
fase-1-diagnostico.md (riesgo ya calificado ahí como el más grave del
módulo: "Crítico (16)" — sin cuenta, sin permisos, cebo irresistible, sin
CSP que lo contenga). No se introdujo nada.
